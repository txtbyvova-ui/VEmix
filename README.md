# VEgroove Automix 2.0 / VEmix 3.0

Конвейер для фоновой музыки в коммерческих пространствах: анализ библиотеки,
редакционный отбор по профилю клиента, «радийная» последовательность треков,
нормализация громкости по EBU R128 с проверкой **закодированного** результата
и автоматический QC.

Два режима вывода:

* **Mode A — Playlist (основной).** Каждый трек — отдельный нормализованный MP3,
  плюс `playlist.m3u8`, `manifest.json` (для будущего веб-плеера) и `tracklist.txt`.
  Треки можно пропускать, повторять и перематывать — **если это умеет плеер**:
  M3U8 — это файл плейлиста, а не плеер.
* **Mode B — Continuous Mix.** Один непрерывный MP3, как раньше, но с новым
  движком переходов (FX только на хвосте уходящего трека, защита пиков в зоне
  перекрытия) и отдельной проверкой громкости итогового микса.

Исходный прототип сохранён без изменений в `legacy/automix_v1.py`;
`automix.py` — обратно совместимая точка входа.

## Установка

Требуется Python 3.11+ и FFmpeg с энкодером `libmp3lame` (и `ffprobe` — рекомендуется;
без него используется менее надёжный разбор вывода `ffmpeg -i`).

```bash
winget install --id Gyan.FFmpeg -e
```

(macOS: `brew install ffmpeg`; Debian/Ubuntu: `sudo apt install ffmpeg`.) После установки
откройте **новую** консоль. Если FFmpeg не в PATH, укажите пути через переменные
`VEG_FFMPEG` / `VEG_FFPROBE` или ключи `--ffmpeg` / `--ffprobe`.

```bash
py -3.12 -m venv .venv
```

```bash
.venv\Scripts\python -m pip install -r requirements-dev.txt
```

`requirements.txt` — точные версии прямых зависимостей; `requirements.lock.txt` —
полный снимок окружения, на котором прогонялись тесты (Python 3.12.10, Windows x64).

Тесты (нужен FFmpeg; интеграционные тесты без него помечаются как skipped с причиной):

```bash
.venv\Scripts\python -m pytest
```

Демо-библиотека из синтетических треков (без чужой музыки) для пробного запуска:

```bash
.venv\Scripts\python examples/make_demo_library.py ./demo_music
```

## Команды

```bash
python automix.py analyze --folder ./music --export-metadata ./curator.csv
```

```bash
python automix.py normalize --folder ./music --output ./normalized --target-lufs -16 --true-peak -1.5
```

```bash
python automix.py playlist --folder ./music --profile ./profiles/client.yaml --metadata ./curator.csv --output ./output --daypart all
```

```bash
python automix.py mix --folder ./music --profile ./profiles/client.yaml --output ./output/mix.mp3
```

```bash
python automix.py qc --folder ./output
```

Старый синтаксис по-прежнему работает и запускает `mix`:

```bash
python automix.py --folder ./music --output ./mix.mp3 --parts 2 --bitrate 320k
```

Ключи, общие для команд, работающих с библиотекой (все, кроме `compare`, у которого только
`--plan`, `--variant`, `--reasons`, `-v`): `--dry-run` (спланировать и напечатать, ничего не
записывать — ни выходов, ни кэша, ни рабочих папок), `--jobs N` (параллельные задания FFmpeg),
`--work-dir`, `--ffmpeg`/`--ffprobe`, `--warnings-ok`, `-v`. Где применимо:
`--metadata` и `--cache` (analyze/playlist/mix/enrich/interpret/plan/suggest; у `render` они
переопределяют значения из файла плана), `--recursive` (у `render` берётся из плана), `--profile`,
`--daypart` (`morning|afternoon|evening|all` или своё имя из профиля), `--seed`, `--duration-min`,
`--max-tracks`; для `mix` и `render --mode mix` — `--crossfade`, `--max-overlap`, `--no-crossfade`,
`--curve`, `--fx` (`clean` по умолчанию; `random` — только явно), `--no-trim-silence`; `--parts` —
только у `mix`. Полный список — `python automix.py <команда> --help`.

### Коды выхода

| Код | Значение |
|-----|----------|
| 0 | PASS |
| 1 | FAIL (провалены проверки, трек не прошёл нормализацию, микс не опубликован); у `analyze` — хотя бы один файл библиотеки не удалось проанализировать (список таких файлов печатается) |
| 2 | ошибка ввода (нет папки, неверный профиль/метаданные/сценарий/ключ, не выбран или не настроен AI-провайдер — неизвестное имя, не задана модель, нет адреса сервера или он не http(s) (модель, которой нет на сервере, — код 5); выход совпал бы с исходником или с входным файлом команды — сценарием, CSV, профилем, кэшем); у `suggest` — модель ответила, но годного черновика нет: отказ, обрезанный, пустой или неразборчивый ответ, черновик невалиден и после повторного запроса |
| 3 | окружение: FFmpeg не найден, нет `libmp3lame` или нужных фильтров; для `interpret`/`suggest` — не установлен SDK провайдера (`requirements-ai.txt`) |
| 4 | WARNING (есть что проверить на слух); у `enrich` — часть запросов не удалась или совпадение неоднозначно; у `interpret` — часть запросов не удалась или ответ модели невалиден (в т.ч. невалидный ответ из кэша, если его не переспросили через `interpret --mode online --retry-invalid`); у `plan` — нарушены жёсткие ограничения в показанном варианте (`--variant`, по умолчанию A; нарушения только в других вариантах дают 0). `--warnings-ok` превращает любой код 4 в 0 |
| 5 | экспорт не выполнен: папка вывода заблокирована, откат публикации, чужие файлы плейлиста в папке вывода, ошибка диска; у `enrich`/`interpret` — не удался ни один запрос (сеть, ключ API, лимит); у `suggest` — AI-провайдер не ответил ни на одну попытку (сеть, ключ API, лимит, сбой сервера, тайм-аут, неизвестная серверу модель) |
| 130 | прервано пользователем (Ctrl+C); в stderr печатается `Interrupted.` |

## Что получается на выходе

**Playlist** (`--output ./output`, с `--daypart all` — подпапки `morning/`, `afternoon/`, `evening/`):

```text
output/
    playlist.m3u8        # #EXTM3U, #EXTINF:<сек>,<Artist - Title>, относительные пути, UTF-8
    manifest.json        # порядок, громкость до/после, признаки и их источники, причины исключений
    tracklist.txt        # человекочитаемый трек-лист
    qc_report.json / qc_report.txt
    tracks/001_Artist_Title.mp3 ...
```

**Mix**: `mix.mp3`, `mix.manifest.json` (таймкоды, переходы, громкость микса, sha256),
`mix_tracklist.txt` (формат v1: `#  | Time | BPM | Key | Xfade | FX | Track`),
`mix_qc_report.json/.txt`.

Пример отчёта QC на синтетической демо-библиотеке — в [examples/sample_output/](examples/sample_output/).

## Громкость (P0)

* Цели по умолчанию: **−16 LUFS**, true peak **≤ −1.5 dBTP**, LRA-цель 11 LU,
  допуски ±1 LU и +0.2 dB. Всё настраивается: `--target-lufs`, `--true-peak`, `--lra`,
  `--lufs-tolerance`, `--true-peak-tolerance`, `--max-dynamic-gain`.
* Двухпроходный `loudnorm`: замер (I, TP, LRA, threshold из JSON FFmpeg — каждое число
  валидируется; true peak берётся максимумом из `loudnorm` (192 кГц) и `ebur128` (×4)) →
  план → второй проход с измеренными значениями в **lossless WAV (float)** → **одно**
  MP3-кодирование → повторный замер **именно MP3** (громкость, true peak, длительность,
  каналы, частота, полное декодирование). Если MP3 вышел за допуск, коррекция
  перекодирует из WAV, а не из MP3. Успешный код возврата FFmpeg доказательством не считается.
* **True peak важнее точного числа LUFS.** Если цель недостижима без превышения пика:
  когда недобор укладывается в допуск ±1 LU — трек выдаётся линейно и проходит; иначе
  выдаётся линейно и безопасно по пику, получает статус **review** и причину.
  Динамический режим `loudnorm` (по сути AGC + лимитер на весь трек) по умолчанию
  **выключен**; включается только явно (`--max-dynamic-gain 2`) и всегда помечается на ревью.
* Высокодинамичные записи не сжимаются: LRA-цель для `loudnorm` не опускается ниже
  измеренного LRA трека (LRA — цель обработки, а не гарантия).
* Особенность `loudnorm`, учтённая в коде: при `measured_LRA = 0` фильтр молча уходит
  в динамический режим, поэтому передаётся 0.01 LU. Фактический режим из JSON второго
  прохода записывается; неожиданный откат в dynamic помечается на ревью.
* Статусы трека: `passed` (проверено на MP3), `review` (выдано безопасно, цель не
  достигнута), `failed` (не опубликовано, причина в отчёте, итоговый статус — FAIL).
* QC сравнивает short-term громкость соседних треков и помечает подозрительные стыки
  для прослушивания (ничего не «дожимает» компрессией).

## Профиль клиента и метаданные куратора

* `profiles/client.yaml` — пример профиля (поп-клиент: en/fr/es/it разрешены, ru исключён,
  предпочтения, дейпарты morning/afternoon/evening). Профиль — это редакционные правила,
  а не загрузка/поиск музыки. Опечатка в ключе — понятная ошибка с подсказкой.
* Языки: многоязычные теги (`rus;eng`) разбираются; исключённый язык исключает трек, если
  он есть **среди** языков трека. Неизвестный язык **не** считается английским: по
  `unknown_policy` трек помечается на ревью или исключается. Кириллица в артисте/названии
  без подтверждённого языка — подсказка, не утверждение «язык = ru»; политика
  `cyrillic_script_policy`. Куратор снимает вопрос, указав язык в CSV.
* Ручные метаданные: `analyze --export-metadata curator.csv` выгружает шаблон (UTF-8 с BOM,
  открывается в Excel; при чтении понимает `;` и десятичную запятую). Заполненные ячейки
  переопределяют автоматику (`--metadata curator.csv`), пустые — нет. Энергия, настроение,
  жанр, «узнаваемость» не выдумываются: без источника остаются неизвестными; авто-оценка
  энергии — эвристика с пониженной уверенностью и явным источником.
* Дейпарты влияют и на отбор (диапазон и «ядро» энергии, теги, жанры, настроения,
  редакционная оценка), и на порядок (кривая энергии, мягкое начало). Трек не повторяется
  между дейпартами; треки, не подошедшие никуда, перечислены в манифесте с причиной.

## Ограничения

* Нет детекции долей/фраз: переходы не выравниваются по сетке. При заметной разнице темпов
  или неизвестном BPM кроссфейд укорачивается и переход помечается «listen».
* «Энергия» из автоанализа — эвристика, проверенная только на синтетике; надёжные значения
  настроения, жанра, языка и узнаваемости даёт только куратор.
* Оценки звучания (как воспринимаются переходы и FX) требуют прослушивания человеком.
* Дейпарты задают отбор и кривую энергии, но отдельных правил стилистической преемственности
  («рабочая атмосфера» днём, «без резких смен стиля» вечером) нет: порядок внутри любого дейпарта
  строится общими весами (настроение/энергия/жанр/темп/гармония). Текст `description` в профиле
  — только пояснение для людей.
* `plan_dayparts`: трек, вытесненный «спокойным» стартом, перераспределяется только в ДРУГИЕ
  дейпарты; в свой он не возвращается, даже если там потом освободилось место (видно в причине
  `not_selected`).
* «no alternative found» в причине помеченного перехода доказано перебором; если доказательство
  получено при резерве спокойного старта, причина прямо говорит «while keeping the calm opening».
* На патологическом контенте (тихая подложка с редкими полномасштабными щелчками) `loudnorm` и
  `ebur128` расходятся до ~1 LU; при расхождении > 0.5 LU трек получает предупреждение
  «meters disagree». На обычной музыке и синтетике расхождение ≤ 0.1 LU.
* Читатель тегов ID3v2 (для мультиязычного `TLAN`) не поддерживает unsynchronisation;
  у таких файлов используется значение `ffprobe` (только первый язык).
* Полный 3.5-часовой микс не прогонялся: RF64-путь и потоковый рендер проверены на коротких
  файлах; память рендера не зависит от длины микса (≈230 МБ на 29-минутном миксе).

## VEmix 3.0: драматургия плейлиста, внешние факты и AI-интерпретация

3.0 добавляет **сценарии** (драматургическая кривая, фазы, якоря, правила), **планировщик** с
явной целевой функцией и альтернативными вариантами, **сегментный аудиоанализ**, **поиск
сведений о треках** в открытых каталогах и **необязательную AI-интерпретацию**. Команды 2.0
без новых аргументов работают как раньше. Архитектура и контракты — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md),
аудит и план — [docs/VEMIX3_PLAN.md](docs/VEMIX3_PLAN.md), отчёт о выполнении — [docs/VEMIX3_REPORT.md](docs/VEMIX3_REPORT.md).

Сведения разных категорий не смешиваются: у каждого значения записан источник, и отчёт показывает,
откуда оно. Категорий шесть:

| Категория | Откуда | Пример |
|---|---|---|
| измерено | анализ файла (`auto:*`) | BPM, тональность, энергия, кривая интенсивности |
| теги файла | ID3 (`id3`), имя файла (`filename`) | жанр, язык |
| куратор | CSV куратора (`manual`) | настроение, роль (`role:`) |
| внешний факт | MusicBrainz / Wikidata (`research:*`) с URL, временем и полями | год релиза, MBID, ISRC |
| вывод по правилам | роли из измерений (`rules:*`), уверенность ≤ 0.5 | «breather» по низкой энергии |
| AI | ответ модели по строгой схеме (`ai:*`), уверенность ≤ 0.8 | настроение «ominous» 0.6 |

### Команды 3.0

```text
analyze   --segments                     сегментный анализ (энергия во времени, плотность, структура, стабильность тональности) в кэш
enrich    --mode online|cache|off        факты из MusicBrainz/Wikidata (+ Discogs, если задан VEG_DISCOGS_TOKEN; --sources), кэш + лимит частоты
interpret --provider ... --mode ...      AI-интерпретация (настроения, роли) по строгой JSON-схеме, кэш
suggest   --brief "..." --output S.yaml  AI-черновик сценария по брифу и обезличенной статистике библиотеки
plan      --scenario S.yaml              полный порядок + причины + альтернативы; --save/--m3u/--csv/--report
compare   --plan plan.json               сравнение вариантов (FFmpeg не нужен)
render    --plan plan.json --mode playlist|mix [--variant B]  рендер варианта (по умолчанию — показанного plan) + QC
qc        --folder ./output              как в 2.0; у выходов render проверяет ещё соответствие плану
```

* **Сеть** нужна только `enrich` и `interpret` в режиме `online` и `suggest` (запрос к AI; если
  ответ не разобрался как JSON-объект или не дал валидного сценария либо ошибка провайдера
  временная — ещё один повторный запрос с перечнем проблем; отказ модели, обрезанный или пустой
  ответ не переспрашиваются; повторы транспорта/SDK — сверх этого). `plan`
  читает кэши фактов и AI (`veg_research_cache.json`, `veg_ai_cache.json` — рядом с кэшем анализа:
  в папке библиотеки или там, куда его перенёс `--cache`). `render` берёт порядок из файла плана, а
  измерения — из кэша анализа (по умолчанию — того, с которым строился план, если файл на месте;
  иначе из папки библиотеки); кэши фактов и AI он не открывает. В сеть не ходит ни одна из этих двух
  команд. `--dry-run` ничего не пишет и сеть не использует.
* **Входы не перезаписываются.** Выходы (`--save`, `--csv`, `--report`, `--m3u`, ...) сверяются с
  исходниками и со входами команды (сценарий, CSV куратора, профиль, план, кэши) — совпадение
  отклоняется с кодом 2.
* **Аудио никуда не отправляется.** AI получает только измерения, описательные проверенные факты
  (год, дата первого релиза, тип релиза, дата публикации по Wikidata) и метки куратора — без путей,
  имён файлов, артиста и названия (модель не должна «вспоминать» песню). С явным
  `interpret --use-community-tags` к ним добавляются непроверенные теги сообщества — теги и жанры
  MusicBrainz (CC BY-NC-SA, некоммерческие) и жанры Wikidata — отдельным блоком с пометкой
  `verified: false`; они уходят и облачному провайдеру, а тег, повторяющий артиста или название,
  отбрасывается. Каждое утверждение модели обязано ссылаться на переданное поле подходящего вида
  (настроение — на энергию/динамику/тональность/метки куратора, «танцевальность» — на ритм), иначе
  отбрасывается. Ключи не задаются флагами — только переменными окружения (для `anthropic`
  учётные данные ищет SDK: также профиль `ant auth login`).
* **Рендер — только командой `render`**: `plan` ничего не нормализует и не кодирует. `render`
  проигрывает сохранённый порядок и отказывается работать, если трек выбранного варианта пропал или
  изменился (размер, время изменения) после планирования (план устарел — запустите `plan` заново).

### Сценарий

Пример — [scenarios/halloween_special.yaml](scenarios/halloween_special.yaml) (Thriller строго
первым, нарастание, первый пик, зловещая передышка, второй разгон, кульминация, контролируемый
спад). Названия треков есть только в конфигурации, алгоритм о них не знает. Сценарий задаёт:
якоря (`position: 1`, `position: -1` или `phase: climax`), обязательные/исключённые треки,
запрещённые и желательные соседства, фазы с долей длительности, целевой энергией и коридором,
роли и настроения фаз (`prefer`/`avoid`), допуски темпа/тональности/скачка энергии, разрешённый
контраст на входе в фазу (больший скачок энергии и смена темпа — `contrast_energy_jump`,
`contrast_bpm_jump`), целевую длительность, правила разнообразия (минимальный зазор между
треками артиста, максимум на артиста, одна версия песни; артист и песня узнаются и по имени, и по
MBID) и веса целевой функции. `curve_axis: tracks` строит кривую по номеру позиции, а не по времени;
`ai_positions` фазы указывает, какие позиции словаря AI (`intro, build, first_peak, breather,
second_build, climax, descent, closer`) считать подсказкой для фазы с другим именем.
`excluded` сопоставляется только точно: исключение отсутствующей «Song (Live)» не исключит
студийную «Song». `--max-tracks` проверяется против якорей, обязательных треков и `min_tracks`
сценария так же, как его поле `max_tracks`; `--duration-min` — в тех же пределах, что
`target_duration_min` (больше 0 и не больше 1440 мин), а допуск `duration_tolerance_min` сценария
при этом сбрасывается на допуск по умолчанию (5 % длительности, не меньше 2 мин). В файле
`use_all_tracks: true` вместе с `target_duration_min`/`max_tracks` — ошибка, а явный флаг важнее:
`--duration-min` или `--max-tracks` без предупреждения отключает `use_all_tracks` сценария, и план
строится как подмножество под заданную длительность или число треков.

Роли: `opener, tension_builder, groove_builder, release, breather, peak, transition, comedown,
closer`. Куратор может задать роль тегом `role:<роль>` в колонке `vibe_tags` CSV (в сходстве
тегов команд 2.0 такие теги не участвуют), настроение — колонкой `mood` (или словом-настроением в
`vibe_tags`). Ручное значение **заменяет** остальные источники того же вида: настроение куратора
откладывает прочие настроения, роль куратора — прочие роли и AI-подсказки позиций (настроение
куратора без роли их не трогает). Отложенное видно в происхождении, но в цель не входит. Без меток
куратора данного вида объединяются AI (уверенность ≤ 0.8), правила (≤ 0.5) и (с
`--use-community-tags`) теги сообщества. Роль оценивается по фазе целиком: если ни одну из ролей
фазы не мог оценить ни один источник (например, фаза ждёт только `tension_builder`, а сегментного
анализа нет) и у AI нет подсказки позиции для этой фазы, роль трека считается неизвестной, а не
«неподходящей»; если оценена хотя бы одна роль фазы, неоценённые считаются несовпадением.

### Отчёт dry-run

Для каждой позиции: номер, фаза, время начала, трек, энергия, цель кривой и отклонение, BPM,
тональность, роль (с пометкой источника), оценка перехода, предупреждения. Ниже — почему трек
стоит здесь (фаза, цель, роли, настроения, переход с ΔBPM/шагами Camelot/ΔE и лучшая
альтернатива для этой позиции: изменение цели и отдельно — какие жёсткие ограничения она
нарушила бы, плюс изменение крупнейших слагаемых — до четырёх с наибольшим |Δ|; все изменившиеся
слагаемые (`term_changes`) — в файле плана `--save`), нарушения жёстких ограничений, компромиссы
вариантов, сомнения в темпе (сегментный анализ не подтвердил BPM — лимит темпа не применяется) и
какие данные отсутствуют или имеют низкую уверенность. Каждый вариант после поиска
«полируется»: ход, который улучшил бы его собственную цель, применяется, а не только
упоминается. Сравнение называет лучший вариант по (тяжесть нарушений, цель). Все числа — из
реально вычисленной целевой функции, не текст «после факта».

### Внешние источники и лицензии

* **MusicBrainz** (основной): поиск записи + собственная переоценка кандидатов (score MusicBrainz —
  это релевантность внутри запроса, а не вероятность: live-версии и спец-миксы тоже получают 100).
  Совпадение применяется автоматически, только если проходят все гейты: оценка ≥ 0.85 (в том числе
  без бонуса за альбом/год), отрыв от второго кандидата ≥ 0.08, длительность известна с обеих
  сторон и расходится не больше чем на 7 с, сходство названия ≥ 0.85 и (если артист известен)
  артиста ≥ 0.80. Иначе статус `ambiguous`, кандидаты — в `--review-csv` для куратора. Если каталог
  ничего не вернул или ни один кандидат не набрал 0.40 — статус `not_found`, в `--review-csv` такие
  треки не попадают. Исключение — MBID записи в тегах файла: ему доверяют, если длительность,
  название и артист ему явно не противоречат. Core data — CC0 (факты).
  **Теги и жанры MusicBrainz — пользовательские данные под CC BY-NC-SA 3.0** (некоммерческие):
  они хранятся отдельно и влияют на план только с явным `--use-community-tags`.
* **Wikidata** (CC0) — только перекрёстная проверка по MBID (дата публикации); противоречия
  между источниками записываются. Жанры Wikidata правятся сообществом — это теги, а не факты:
  они, как и теги MusicBrainz, влияют на план только с `--use-community-tags`.
* **Discogs** — при `VEG_DISCOGS_TOKEN` подключается автоматически (или `--sources`); по
  условиям API данные не старше 6 часов (TTL кэша 6 ч, в `--report` просроченное удаляется),
  атрибуция «Data provided by Discogs.» стоит рядом с каждым значением и в выводе консоли.
* Альбом и год из тегов файла помогают выбрать между равноценными кандидатами (например,
  ремастер против оригинала), но никогда не превращают слабое совпадение в принятое.
* **Bandcamp, Last.fm, AcoustID — не реализованы**: у Bandcamp нет публичного API и запрещён
  скрейпинг, Last.fm — только некоммерческое использование, AcoustID требует отправки отпечатка
  аудио (нужно явное согласие) и платного плана для коммерческого использования.
* MusicBrainz требует User-Agent с контактом: задайте `VEG_CONTACT` (e-mail или URL); по
  умолчанию используется адрес проекта. Частота — не чаще 1 запроса в 1.1 с.

### AI-провайдеры

| `--provider` / `VEG_AI_PROVIDER` | Что нужно | Модель |
|---|---|---|
| `anthropic` | `pip install -r requirements-ai.txt`; ключ — `ANTHROPIC_API_KEY` (или профиль/`ANTHROPIC_AUTH_TOKEN`) | по умолчанию `claude-opus-5-5`, `--model`/`VEG_AI_MODEL` |
| `ollama`, `lmstudio`, `llamacpp`, `openai-compatible` | локальный или OpenAI-совместимый сервер; адрес — `--base-url` (у `interpret`/`suggest`) или `VEG_AI_BASE_URL`, обязателен только для `openai-compatible`; по умолчанию `ollama` — `OLLAMA_API_BASE` + `/v1`, иначе http://localhost:11434/v1, `lmstudio` — http://localhost:1234/v1, `llamacpp` — http://localhost:8080/v1; ключ — `VEG_AI_API_KEY` (для локальных необязателен; `OPENAI_API_KEY` отправляется **только** на `*.openai.com`, чтобы глобальный ключ не уходил на чужой сервер) | обязательно `--model` / `VEG_AI_MODEL` |

Для Claude включён серверный fallback при отказе модели (`VEG_AI_FALLBACKS=off` — выключить).
Ответ проверяется по схеме; утверждения без ссылки на реально переданные данные отбрасываются
(видно в отчёте как `dropped`). Ответы кэшируются: повторный `plan` бесплатен и воспроизводим —
и после истечения TTL фактов (90 дней; ответы «не найдено» — 14 дней): ещё год после истечения
режим `cache` продолжает использовать записи MusicBrainz/Wikidata, помечая их устаревшими
(`stale`), затем они удаляются из кэша (`STALE_RETENTION_S`); обновить — `enrich --mode online`.
Данные Discogs старше 6 ч не используются (условия API).
Без провайдера всё работает на измерениях и правилах.

### Ограничения 3.0

* Роли из правил и «прокси вокала» — эвристики на синтетике, уверенность намеренно низкая;
  разметка структуры (intro/build/break/outro) — без ML, это кандидаты, а не «куплет/припев».
* Кривая строится по длительностям исходников: в непрерывном миксе границы фаз сдвигаются на
  длину кроссфейдов и обрезанной тишины.
* Тональные лимиты сценария жёсткие только для ручных тональностей (порог уверенности 0.6);
  авто-тональность 2.0 откалибрована не выше 0.5 и жёстким лимитом не бывает: превышение лимита на
  таком переходе нарушением не считается, отчёт лишь добавляет к нему предупреждение «… — not enforced».
* `use_all_tracks` работает до 600 кандидатов (размер матриц переходов); больший пул —
  ошибка сценария с подсказкой задать `max_tracks`/длительность или сузить пул.
* Поиск оптимизатора эвристический с фиксированным бюджетом: отчёт говорит «не удалось
  избежать», а не «доказано, что невозможно».
* Реальные сервисы (MusicBrainz, Claude, Ollama) в тестах не вызываются — только подменённые
  транспорты и клиенты.
